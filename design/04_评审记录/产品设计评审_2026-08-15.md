# EngForge 产品设计评审（中立视角）

> **评审日期**：2026-08-15
> **评审对象**：产品理念（规划书 v2.0）+ HTML 交互原型 + 已实现 Phase 1 应用
> **评审立场**：中立点评——每个论点同时给出「成立的理由」和「存疑的理由」，不下绝对结论
> **与前一份审核的关系**：`DESIGN_AUDIT_代码审核_2026-08-14.md` 聚焦代码工程质量，本文聚焦**产品与设计决策本身**

---

## 一句话总结

EngForge 的核心理念（写作即仓库）在同类产品中有真实差异化，产品治理机制（墓碑三锚点）罕见地成熟；但 GitHub 隐喻的迁移成本、同伴反馈的质量天花板、邀请制冷启动三个结构性风险，目前都还没有被产品层面的设计回答。

---

## 一、理念理解（先对齐，再点评）

产品的底层逻辑是一条完整类比：

| GitHub 概念 | EngForge 对应物 | 解决的痛点 |
|-------------|----------------|-----------|
| Repository | 每篇作文/翻译 | 范文是"成品"，看不到修改过程 |
| Fork | 借鉴范文到自己工坊改写 | 背了范文不会用 |
| Pull Request | 邀请伙伴逐句批改 | 写完没人改、改得不专业 |
| Commit / 版本历史 | 从初稿到终稿的每一步 | 进步不可见、无法回顾 |
| Star | 个人语料库收藏 | 词汇书不如真实语料实用 |
| 默认私有仓库 | 作文默认私密 | 作文是隐私资产 |

三条墓碑锚点：**身份锚**（只做考研/高考写作，不做泛英语）、**生存锚**（AI 只标错和给词汇建议，禁代写）、**信任锚**（默认私密）。

这套理念的内在一致性是成立的：所有机制都服务于「主观题练习的反馈缺失 + 过程不可见」，且互相咬合（PR 产生版本历史 → 版本历史让进步可见 → Star 沉淀优质结果）。产品治理章节（防自我漂移的决策日志 + 纠偏预检）超出了大多数个人项目的成熟度。

## 二、存疑点逐条点评

### 2.1 GitHub 隐喻 vs 目标用户的认知迁移成本

**支持面**：隐喻只是交互骨架，用户感知到的是「我的作文有历史记录」「同学帮我改了这几句」——不需要理解 Fork/PR 术语也能获得价值。GitHub 自身也是 invite-only 起步，工具价值先于概念传播。

**存疑面**：考研/高考生里 GitHub 用户的比例极低。「Fork」「PR」对他们是黑话而不是 affordance。原型的处理暴露了这个矛盾——Landing 页三个特性卡只能用字母 F/P/S 当图标，说明**视觉系统无法自解释这套隐喻**。如果每个概念都需要一段文案解释（"复制范文到自己的工坊"），隐喻的沟通成本就开始吃掉它的组织收益。

**观察建议**：观察真实用户第一次使用时，"Fork"和"提交批改"哪个词更快被理解。如果隐喻词必须永远带注释，值得考虑只在系统内部保留 git 语义、界面层改用学习场景词汇（"借鉴改写"“求批改"）。

### 2.2 「同学互改不专业」的痛点，被「PR 同学互改」解决了吗

**支持面**：规划书的逻辑不是"同伴更专业"，而是"结构化对话比简单打分好"——PR 强迫批改者指明改了哪句、为什么改，这确实比"写得不错，继续加油"有信息量。版本历史也让"怎么从平庸到优秀"变得可见，这是对"范文都是成品"痛点的直接回应。

**存疑面**：结构化能提升反馈的**形式质量**，无法提升**内容质量**。一个不知道 "good→beneficial" 该不该改的同学，在 PR 界面里依然不知道。**核心问题**：产品的价值上限 = 同伴圈子的英语水平上限。原型 Detail 页的评论（王同学指出 phubbing 例子、张同学建议问句开头）描绘的是一个理想化的高水平小圈子——真实的高中生圈子未必凑得出来。

**观察建议**：这是产品最本质的赌注。建议在内测期明确度量「批改被采纳率」和「批改者水平分布」——如果 80% 的有效批改来自 top 20% 的用户，说明产品实际是"高手工具+围观学习"，那界面设计应该向"展示高手批改过程"倾斜，而不是均衡的互改。

### 2.3 邀请制冷启动的鸡生蛋问题

**支持面**：邀请制与信任锚（默认私密）天然一致，避免空广场的劝退效应，GitHub 有先例。原型里"剩余邀请名额 3/5"的稀缺感设计也是对的。

**存疑面**：GitHub 的 invite-only 时代用户本来就是开发者，EngForge 的邀请链依赖**现实中恰好有英语水平不错又愿意用工具的同学**。考研是竞争关系（尤其同校同专业），"邀请同学改我的作文"存在真实的心理门槛。5 人名额 × 7 天有效期的传播系数可能 < 1，即每代用户带来的新用户不足 1 人——工具再好用也会缓慢衰减。

**观察建议**：冷启动期不妨把「邀请」的语义从"拉同学"扩展为"绑定学习搭子/研友"，后者在考研语境里是现成的社会关系，不需要发明新行为。

### 2.4 AI 护栏承诺与 11 词词库的落差

**支持面**：L1/L2/L3 三层护栏 + "AI 只标注不代替思考"的产品哲学，是这个产品最清醒的决策——它保住了社区协作的差异化价值，避免了沦为又一个 AI 代写工具。

**存疑面**：**关键发现**：Phase 1 客户端词库只有 11 个词，实际几乎扫描不出标注。这意味着早期用户看到的"AI 标注"承诺基本是空的。护栏划得很好，但护栏里面还没有货。规划书自己也承认 LLM 要到 Phase 3——中间隔着整个 Phase 2 的空窗期，期间产品的 AI 卖点依赖 11 个词撑门面。

**观察建议**：要么在 Phase 2 提前做一个轻量规则引擎（高频口语词替换表，几百词规模，仍是客户端可实现的"词汇升级"），要么在界面上诚实降级 AI 面板的权重，别让它占据编辑器右侧一整栏却经常空转。

### 2.5 双人群（考研 + 上海高考）的未分化

**支持面**：两类用户的练习形态（大作文/翻译/反复打磨）确实同构，一套 Fork/PR 机制可以复用，Phase 1 不分人群是合理的资源决策。

**存疑面**：两类人群的**内容生态**完全不同——考研图画作文 vs 上海高考概要写作，语料、范文、批改标准互不通用。当工坊内混入两类用户互相批改时，反馈质量会打折。原型对此零处理（标签有"考研大作文/高考作文"，但没有人群维度的匹配机制）。

**观察建议**：不需要现在做，但数据模型里应该尽早有 user 的备考身份字段（哪怕只是 profile 一个 enum），否则后期做批改匹配和内容推荐时无数据可用。

### 2.6 游戏化节奏与写作频率的错位

**支持面**：热力图/连续天数对备考用户有明确的激励价值，"看得见的进步"正是核心痛点之一。

**存疑面**：GitHub 热力图成立的前提是**高频小颗粒行为**（每天多次 commit）。写作是低频大颗粒行为——一周认真写 2-3 篇已是高投入。原型展示"连续 47 天"的热力图，隐含的期望是每天都打开，但产品没有设计"每天值得点一下"的轻量行为（词汇积累？句子精读？——后者被降级为附属功能了）。**存疑点**：热力图可能长期大面积空白，反而传递"我不够努力"的挫败感。

**观察建议**：热力图的计数单位考虑从"天"放宽到"周格子按篇数着色"，或把 AI 词汇修改确认这类轻行为也计入——让热力图反映真实投入节奏而不是伪造 GitHub 式日活。

### 2.7 三份设计事实源的漂移（设计工程问题）

**现状**：HTML 原型（Phase 0）→ Ardot 设计稿（Bento Neutral）→ 已实现代码，三者并存且原型已明显落后：

- 原型仍是单字符图标（F/P/S/H），代码已全面换 lucide-react
- 原型展示评论/学习目标/通知红点/邀请码弹窗——其中**评论和学习目标不在 Phase 1 边界内**，属于超范围承诺
- 原型的深色 Sidebar 已被浅色 Pill 样式取代

**风险**：原型还在被当作"产品意图的参考"，但它展示的期望与实际交付的差距会持续制造认知混乱（比如测试同学按原型验收，会发现功能"缺失"）。

**决策建议**：本次整理已把原型归档为历史参考（见 `design/README.md` 的优先级规则）。深度重构原型时直接基于 Ardot 设计稿重画，并**按 Phase 1 真实边界裁剪功能展示**——原型展示未实现功能是双刃剑，对内可以是对齐方向的愿景图，对外（哪怕只是测试同学）就是虚假广告。

## 三、总体判断

**理念层（强）**：痛点选择准确（主观题反馈缺失是真实且未被满足的），隐喻体系自洽，产品治理机制（墓碑/日志/预检）是个人项目里罕见的自律设计。

**设计层（中）**：视觉系统已经通过 Bento Neutral 迁移补课，但隐喻的沟通成本（图标/文案无法自解释）和原型-实现的漂移还没有系统解决。

**风险层（集中）**：三个结构性风险——同伴反馈质量天花板、邀请制传播系数、AI 空窗期——都不是界面问题，而是产品假设问题。内测期最值得收集的数据就是去验证这三个假设，而不是急着加功能。

---

## 四、对「深度重构原型」的前置建议

1. **以 Ardot 设计稿为底**重建，不要修补 HTML 原型（漂移已不可逆）
2. **隐喻降皮**：界面词汇用学习场景语言，git 术语只留在系统内部（数据表、日志）
3. **按真实边界裁剪**：Phase 1 有的才画，Phase 2 的功能用"即将上线"的占位规范表达，不画完整交互
4. **补三处原型从未回答的设计**：空状态（新用户 0 作文 0 协作者时每个页面长什么样）、批改质量引导（PR 界面如何帮不会改的人给出有用反馈）、AI 空窗期的面板降级样式
5. 响应式（≥1024px 可用）在原型阶段就要定断点策略，代码层已欠此债
